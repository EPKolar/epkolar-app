Freigabe Inhaber 19.11.2026, Betriebsvereinbarung unterschrieben. Zweig `feature/kameras-phase1`
(Basis v3.9.1052 = 525c606). **Nichts davon ist live:** kein SQL eingespielt, keine Edge Function

## 1. Grundsatz: der Schutz sitzt am Server

Lehre aus `fz_finanzen`: was der Client versteckt, ist nicht geschützt. Darum entscheidet über jedes
Videobild **die Edge Function** `kamera-stream` – und dort zuerst die Datenbank-Funktion
`kamera_darf_sehen`. Die App zeigt nur an, was der Server erlaubt. Ein Monteur bekommt **an keiner
Stelle eine Stream-Adresse**: weder die Tabelle `kameras` (enthält keine), noch `kamera_backend`
(nur Server), noch die Edge Function (Rollensperre vor jeder weiteren Abfrage).

## 2. Datenmodell

| Tabelle | Inhalt | Wer liest | Wer schreibt |
|---|---|---|---|
| `kameras` | id, name, standort, hersteller, modell, aktiv, aufbewahrung_tage (1–30, Standard 3 = 72 h), created_at, updated_at | Admin (Verwaltung) **oder** wer die Kamera jetzt sehen darf | nur Admin |
| `kamera_backend` | kamera_id → stream_name (go2rtc), aufzeichnung_quelle (Frigate) | **nur service_role** (RLS an, keine Policy, keine Rechte für anon/authenticated) | nur service_role (SQL im Dashboard) |
| `kamera_zugriff` | je Kamera × (Rolle **oder** Nutzer): wochentage (ISO 1=Mo … 7=So), von, bis, erlaubt, bemerkung | nur Admin | nur Admin |
| `kamera_abruf_log` | jede Stream-Anfrage: Zeit, Nutzer, Kamera, scope, erteilt/abgelehnt, Grund | nur Admin | nur die Edge Function (service_role) |

- **Keine Stream-Adresse, kein Zugangsdatum** in einer Tabelle, die ein Client lesen kann.
  Kennwörter der Kameras stehen nirgends in Datenbank oder Repo – nur in der go2rtc-/Frigate-Konfiguration
  auf dem Video-Host.
- Kein CASCADE. Fremdschlüssel `ON DELETE RESTRICT`; die App bietet „deaktivieren“ statt löschen.
- `aufbewahrung_tage`: CHECK 1..30. Regelfall nach § 13 Abs. 3 DSG sind 72 Stunden (= 3 Tage);
  längere Fristen brauchen eine Begründung (siehe offene Fragen).

### Rollen

Kamerarollen sind **genau** `admin`, `projektleiter`, `buero`, `lagerleitung` (Feld `users.role`),
als ausdrückliche Liste – **nicht** `is_staff()`, das `lagerleitung` nicht kennt. Jede andere Rolle
(monteur, helfer, techniker, obermonteur, lager_display, stempel_terminal, anon) sieht **nie** eine
Kamera – auch nicht über eine eigene Nutzer-Freigabe, weil die Rollenprüfung vor den Regeln steht.
Der Nutzer muss aktiv und nicht gesperrt sein (`users.active`, `users.locked`, typ-agnostisch geprüft).

## 3. Vorrang der Zugriffsregeln

Ausgewertet in `public.kamera_pruefen` zur **Wiener Ortszeit** (`Europe/Vienna`, Sommerzeit-sicher):

| Stufe | Bedingung | Ergebnis |
|---|---|---|
| 0 | Rolle keine Kamerarolle, Nutzer inaktiv/gesperrt, Kamera inaktiv/unbekannt | **NEIN** (hart) |
| 1 | Nutzer-Regel `erlaubt=false`, Fenster trifft | **NEIN** |
| 2 | Nutzer-Regel `erlaubt=true`, Fenster trifft | JA |
| 3 | Rollen-Regel `erlaubt=false`, Fenster trifft | **NEIN** |
| 4 | Rollen-Regel `erlaubt=true`, Fenster trifft | JA |
| 5 | sonst | **NEIN** (Standard) |

Kurz: **Nutzer-Sperre > Nutzer-Freigabe > Rollen-Sperre > Rollen-Freigabe > Standard-Nein.**

- Einen einzelnen Projektleiter für eine Kamera aussperren: Regel „Person = dieser PL, Sperre“, ohne
  Zeitfenster (= immer). Die Rollen-Freigabe für alle anderen PL bleibt bestehen.
- Fenster: `wochentage` (mindestens einer), `von`/`bis` beide leer = ganzer Tag, sonst `von < bis`,
  `bis` exklusiv. Über Mitternacht = zwei Regeln.
- Auch der Admin sieht ein Bild nur mit passender Regel (keine stille Admin-Ausnahme); verwalten darf er immer.
- Der ausführbare Spiegel der Regel steht in `logic.ts` (`entscheide`) und wird in den Tests benutzt.

## 4. Serverprüfung und Token-Vertrag

Ablauf der Edge Function `kamera-stream` (vollständig im README der Function):

1. JWT prüfen (`auth.getUser`) → sonst 401
2. Nutzerzeile aktiv, nicht gesperrt → sonst 403
3. Rolle ∈ Kamerarollen → sonst 403 (**vor** jeder Kamera-/Backend-Abfrage)
4. Secrets vorhanden → sonst 503
5. Anfrage gültig → sonst 400
6. Aufzeichnung nur mit `geraet=pc` **und** Rolle in `KAMERA_AUFZEICHNUNG_ROLLEN`
   (Standard admin, projektleiter, buero; Lagerleitung nur live) → sonst 403
7. `kamera_darf_sehen(kamera)` mit dem **JWT des Aufrufers** und **ohne** Zeitangabe (DB nimmt `now()`) → sonst 403
8. Backend-Zuordnung (service_role) → sonst 503
9. Token signieren, Adresse zurückgeben, Abruf protokollieren

Fehler tragen nur `{error:<Code>}` – keine Adresse, kein Streamname, kein Grund. CORS nur
`https://epkolar.github.io`.

**Token** (der Reverse-Proxy prüft genau das):

```
T = base64url(JSON) "." base64url(HMAC-SHA256(KAMERA_TOKEN_SECRET, erster Teil))
JSON = {v:1, k:<kamera_id>, s:<stream|quelle>, u:<users.id>, sc:"live"|"aufzeichnung", iat, exp, n:<nonce>}
exp - iat <= 120 s (Standard 90), Uhrversatz <= 5 s, Pfad-Stream == s, Pfad-Art == sc
```

Adressen: `<BASIS>/live/<stream>/index.m3u8?token=…` (LL-HLS), `<BASIS>/live/<stream>/whep?token=…`
(WebRTC/WHEP), `<BASIS>/aufzeichnung/<quelle>?token=…&von=<unix>&bis=<unix>`.
Das Token gilt für den **Aufbau** einer Sitzung; die App holt etwa 20 s vor Ablauf ein neues
(HLS lädt die Playlist damit neu). Antwortet der Server beim Erneuern mit 403 (Zeitfenster vorbei,
Regel entzogen), schließt die App das Bild sofort.

## 5. Schalter (Feature-Flag)

**Für Projektleitung, Büro und Lagerleitung in Produktion AUS. Nichts schaltet sich selbst ein.**
Seit dem Zweig `feature/kameras-app` (19.11.2026, Auftrag Inhaber) sieht der **Admin** den Bereich in Produktion
(Code-Konstante `KAMERAS_ADMIN=true`) – zuerst mit der Ansicht **Einrichtung** (siehe `PHASE2_2026-11-19.md`, Abschnitt 6).

| Weg | Bedingung | Phase 1 |
|---|---|---|
| Admin (seit feature/kameras-app) | Rolle **admin** und `KAMERAS_ADMIN=true` | an; alle anderen Rollen unverändert aus |
| Produktion | Code-Konstante `KAMERAS_PROD=true` **und** `system_config.kameras_aktiv = true` | Konstante steht auf `false` → dieser Weg wird nicht einmal gelesen |
| Testbetrieb | Rolle **admin** **und** `system_config.kameras_testumgebung = true` **und** lokaler Testschalter auf diesem Gerät | einziger Weg zum Ausprobieren |

- Lokaler Testschalter: App mit `?kameras_test=1` öffnen setzt ihn (localStorage `epk_kameras_test`),
  `?kameras_test=0` löscht ihn. Für jede andere Rolle als Admin wird der Parameter ignoriert.
- `kameras_testumgebung` setzt nur ein Admin in `system_config` (vorhandene Admin-Konfig bzw. SQL).
  Fehlt der Eintrag oder ist er nicht `true`, bleibt alles aus – auch mit lokalem Schalter.
- Ohne Schalter: kein Reiter, die Ansicht ist nicht erreichbar, **kein einziger Abruf** (auch
  `system_config` wird nur gelesen, wenn ein Admin den lokalen Schalter gesetzt hat).
- Zusätzlich gilt immer: Reiter und Ansicht nur für die vier Kamerarollen; Monteure sehen nie etwas.

## 6. App-Bereich „Kameras“

| Gerät | Inhalt |
|---|---|
| Handy / Tablet (unter 1200 px oder ohne feinen Zeiger) | nur **Live**: Raster Einzel / 2×2 / 3×3 / Alle (am Handy höchstens 2 Spalten), Kacheln holen ihre Adresse je Kachel vom Server |
| PC (ab 1200 px **und** feiner Zeiger) | Live + **Aufzeichnungen** (admin/PL/Büro; Tag aus der Aufbewahrungsfrist, Zeitleiste, Abruf mit `scope=aufzeichnung`) + **Verwaltung** (nur Admin) |

- Ohne Video-Backend (Function nicht deployt, 404/503) zeigen die Kacheln „Kein Video-Backend verbunden“.
- Fehlen die Tabellen (404/42P01/PGRST205), steht dort „Datenmodell noch nicht angelegt“.
- Player: WebRTC (WHEP) bevorzugt, sonst natives LL-HLS (Safari); Adressen werden nur mit `https://`
  geladen. Aufzeichnungs-Wiedergabe im Browser kommt mit dem Video-Host (HLS-Player) – Phase 1 zeigt
  dort den Hinweis.
- Verwaltung: Kameraliste (Status aktiv/inaktiv, Aufbewahrung), Anlegen/Bearbeiten, „Zugriff je Kamera“
  mit Rollen-Chips, Personen (nur Kamerarollen wählbar, Monteure nicht), Freigabe/Sperre, Wochentags-Chips,
  Zeitfenster; Liste nach Vorrang sortiert. Streamnamen und Kennwörter werden hier **nicht** gepflegt.
- Schreibwege direkt über `_sbUpsert`/`_sbPost`/`_sbDelete` (RLS prüft Admin). **Bewusst nicht** über die
  SyncQueue: eine offline gemerkte Zugriffsregel, die Stunden später nachgespielt wird, wäre bei einer
  Überwachungsfreigabe die falsche Wirkung; außerdem müsste dafür `ROUTE_MAP` angefasst werden.
- Aussehen: EP-Kolar-CI (#009640, Knöpfe bpS/bsS/bdS, Blau nie als Knopf), Hell/Dunkel über die
  vorhandenen Token, eigene Linien-Ikone `videokamera`, tabellarische Ziffern, Tippziele ≥ 44 px,
  Schrift nur über `UI.f*` (≥ 12 px), kein Querlauf bei 390 px (Raster mit `minmax(0,1fr)`, Umbrüche).

## 7. Was die Infrastruktur liefern muss

1. **Video-Host** mit go2rtc (Live: WebRTC/WHEP + LL-HLS) und Frigate (Aufzeichnung), Kameras per RTSP
   im getrennten Netz; Zugangsdaten nur in dessen Konfiguration.
2. **QNAP-Speicher** für Aufzeichnungen; automatische Löschung nach `kameras.aufbewahrung_tage`.
3. **Reverse-Proxy** (TLS, öffentlich einziger Eingang): prüft jedes Token nach dem Vertrag im README
   (HMAC konstantzeitig, `v`, `exp`, Pfad = `s`, Art = `sc`), leitet nur die erlaubten Pfade weiter,
   alles andere 404; go2rtc-/Frigate-Oberflächen und -APIs nie öffentlich.
4. **WireGuard** zwischen Büro und Standorten; keine Portfreigaben zu Kameras.
5. **Secrets** der Edge Function: `KAMERA_TOKEN_SECRET` (≥ 32 Zeichen, nur Function + Proxy),
   `KAMERA_BACKEND_BASE` (https), optional `KAMERA_TOKEN_TTL`, `KAMERA_AUFZEICHNUNG_ROLLEN`.
6. Pflege `kamera_backend` (Streamname je Kamera) per SQL durch den Admin.

## 8. Reihenfolge der Inbetriebnahme

1. SQL-Entwurf prüfen, Probe-Block in einer Transaktion fahren (BEGIN … ROLLBACK), dann einspielen.
2. Infrastruktur aufbauen, Proxy gegen `pruefeToken` (logic.ts) abgleichen.
3. Edge Function deployen (beide Dateien), Secrets setzen.
4. `system_config.kameras_testumgebung = true`, Admin testet mit `?kameras_test=1`.
5. Pilot (Testplan unten). Erst danach: `KAMERAS_PROD=true` per Release + `kameras_aktiv = true`.

| # | Konto | Schritt | Erwartet |

## 10. Offene Fragen (Entscheid Sebastian)

1. **Lagerleitung über `users.rolle`:** die App erkennt Lagerleitung teils über das Anzeigefeld `rolle`.
   Die Kamera-Prüfung nimmt **nur** `users.role`. Ein Konto mit `rolle='Lagerleitung'`, aber
   `role='monteur'`, sieht keine Kamera. Gewollt so (sicherer), oder soll das Lagerleitungskonto
   `role='lagerleitung'` bekommen?
2. **Aufbewahrung:** Standard 3 Tage (72 h, DSG-Regelfall), Obergrenze 30. Passt das zur Betriebsvereinbarung?
3. **Aufzeichnung und Zeitfenster:** Phase 1 prüft beim Abruf einer Aufzeichnung das Fenster des
   **Abrufzeitpunkts**, nicht des aufgezeichneten Zeitraums. Soll ein PL mit Fenster Mo–Fr auch
   Samstagsaufnahmen sehen dürfen?
4. **Protokoll:** `kamera_abruf_log` hält jede Anfrage fest (wer, wann, welche Kamera). Löschfrist und
   Einsicht (nur Admin? Betriebsrat?) laut Betriebsvereinbarung festlegen.
5. **Admin ohne Regel:** auch der Admin braucht eine Regel, um ein Bild zu sehen. Beibehalten?
6. Aufzeichnungs-Player im Browser (hls.js o. ä.) und Abschnittsliste (Frigate) kommen mit dem Video-Host.
